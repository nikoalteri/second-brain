# Plan 25-03 — review and idempotent confirmation

## Objective

Let the owner edit, discard and confirm draft rows into real `Transaction` / `CreditCardExpense` records, exactly once.

## Read first

`25-RESEARCH.md` (decision 7), `25-02-SUMMARY.md`, `TransactionController::store`, `CreditCardExpenseService`, `TransactionObserver`, `AccountBalanceService`, `SubscriptionService::upsertTransaction`/`upsertCreditCardExpense`.

## Work

1. `GET .../rows` (filter by status/duplicate class), `PATCH .../rows/{row}` (category, amount correction, description, discard/restore) with ownership checks.
2. `ImportRowPromotionService`: DB transaction, `lockForUpdate` on the row, status must be `draft`, build the record through the same model/service path as the manual API (type from sign, ownership checks, card cycle resolution), store the created id on the row, set `confirmed`. Unique constraint on promoted ids. Rows that cannot be promoted get an explicit reason, never a guess.
3. `POST .../confirm` for selected rows or all non-flagged rows, with per-row outcomes and safe retry; batch status derived from its rows.
4. Tests: balance moves once; double and concurrent confirm; deleted/inactive target; card without a cycle; both target types; a card charge plus account payment case; other users' IDs.

## Acceptance

Balances, budgets and reports change only on confirmation and exactly once; a failed row never blocks the others.

## Output

`25-03-SUMMARY.md`.
