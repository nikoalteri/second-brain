# Plan 25-05 — close the import/ledger concurrency gap

**Origin:** PR #76 review (2026-10-17, 13:40). The duplicate re-check in `ImportRowPromotionService::confirm()` runs before the insert, so a movement committed in between is missed; the unique promotion indexes only protect the retry of the *same staging row*, not two distinct ledger rows for one real charge. `autonomous: false`: the lock protocol touches writers outside the import, so the maintainer approves it before code.

## Objective

Make "re-check for duplicates, then insert" atomic with respect to every other path that can produce the corresponding ledger movement, without a deadlock-prone lock order and without locking more than the one account or card involved. Prove it with two real MySQL connections.

## What the code does today (verified)

- **Account balance:** every `Transaction` insert/update/delete moves `accounts.balance` through `TransactionObserver` → `AccountBalanceService` (an `UPDATE`), i.e. the account row is write-locked only *after* the insert. No writer takes it *before*. SQLite ignores `FOR UPDATE`.
- **Card expenses:** `CreditCardExpenseObserver::creating` → `CreditCardExpenseService` already takes the **card row** (`lockForUpdate`, ascending ids) before inserting, inside the caller's transaction; `CreditCardCycleService` documents "card row first, then cycles/payments".
- **Ledger writers (all of them):** `TransactionController::store` (DB::transaction), GraphQL `createTransaction` (Lighthouse `transactional_mutations: true`), Filament transaction pages (`AdminPanelProvider::databaseTransactions()` is on), `AccountTransferService` (two legs, one transaction), `LoanPaymentPostingService`, `CreditCardPaymentPostingService`, `SubscriptionService::upsertTransaction` / `upsertCreditCardExpense` (each in a transaction), `CreditCardExpenseController`, and the import. Restoring a soft-deleted `Transaction` also produces a movement.
- **Existing lock orders to respect:** subscription row → (card row | account); card row → cycle/payment rows; payment row → account (posting) → card (cycle sync) in `markPaid`.
- **Pre-existing hazard found:** `AccountTransferService` creates the `out` leg (touching account A) before the `in` leg (account B): two opposite transfers A→B and B→A can deadlock today. The protocol below fixes it as a side effect.
- **MySQL:** `mysqld` 26.7 and `pdo_mysql` are available locally; nothing is running. The suite is SQLite-only (`phpunit.xml`).

## Protocol (one rule)

> A write that can create, move or restore a ledger movement first takes the **target row lock** — `accounts` row for `Transaction`, `credit_cards` row for `CreditCardExpense` — *before its first plain read and before the insert*, inside its own database transaction, and keeps it until commit. Several accounts are locked in one statement ordered by ascending id. Account locks come **before** card locks; domain locks (import batch, subscription, payment/loan rows) come **before** both.

Why this closes the race: a writer that already holds the target lock makes the import wait; when the import gets the lock it re-reads the ledger, and a first read after the lock sees everything committed before it (InnoDB takes the read snapshot at the first plain SELECT, so the lock must come first — the import's transaction starts with locking reads only). If the import holds the lock, the other writer waits and inserts afterwards. A manual entry is never blocked from existing; it just cannot interleave inside the import's check-and-insert.

## Work

1. **`LedgerLock`** (small service/trait): `accounts(array $ids)` — one `SELECT … WHERE id IN (…) ORDER BY id FOR UPDATE` (soft-deleted accounts included); `card(int $id)`; both no-ops outside a transaction level >0 are *not* allowed to silently pass: they log a warning with the caller, so a future unwrapped writer is visible.
2. **Hook every writer** (central, not per call site): `TransactionObserver` `creating` (lock `account_id`), `updating` when `account_id`/`amount`/`date` change (lock old and new account together), `restoring`. Card expenses already lock the card in `creating`; keep that and reuse `LedgerLock::card` so the rule lives in one place.
3. **`AccountTransferService`:** lock both accounts ascending at the start of its transaction (removes the A→B / B→A deadlock).
4. **Import promotion:** transaction order becomes *batch row → target row (account or card) → staging row*, with no plain read before the target lock. Under the locks, run a **single-row re-check** (`ImportDuplicateDetector::matchOne`): same candidate rules as today, excluding ledger movements already posted by this batch and ledger ids already claimed by other draft rows' stored matches (keeps the one-to-one matching and two identical legitimate charges). If a row that was reviewed as clean now matches, store the new classification and skip it with "review it again"; a row the owner already saw flagged proceeds (conscious duplicate). The pre-pass in `confirm()` stays for the `all_ready` selection.
5. **Docs:** a lock-order note beside the card one (`CreditCardCycleService` docblock) and in the phase summary.

## Tests

- **SQLite (default suite):** query-order tests in the style of `CreditCardLockOrderTest` — the target lock statement precedes the first ledger read and the insert for the import, a manual create, a transfer, a posting and a restore; single-row re-check unit tests (new match → skipped, flagged → proceeds, identical legitimate charges, claimed ids); transfer locks both accounts ascending. No behaviour regression: the existing 753 tests stay green.
- **MySQL, two real connections (new, opt-in):** `phpunit.mysql.xml` + a `tests/Mysql` group that migrates a throwaway database and drives a second PHP process with file-based barriers for deterministic interleaving. Cases: (a) a manual create holding its uncommitted insert while the import promotes → the import waits, then holds the row back; (b) the import holding the lock after its check while a manual create starts → the manual create waits and both end consistent; (c) two concurrent imports of the same line; (d) the same staging row confirmed twice at once → balance moves once; (e) a subscription/loan/card-payment posting racing the import; (f) opposite transfers A→B and B→A → no deadlock; (g) two identical legitimate charges in one batch and an explicit duplicate choice still post. A short recipe (start a scratch `mysqld` on a spare port, run the group) goes in the phase summary. CI is not changed.
- **Browser (25-04 completion, the third request):** review `StatementImportView`/store against the final API and check desktop and mobile with synthetic data: delimiter choice (including the ambiguous-file error), rows to review, partial results, retry of a failed row.

## Risks and open points

- **Throughput:** the account row becomes a short serialisation point for writes to that account; transactions already update that row, so the added wait is the portion before the insert. Locks are held only for the transaction.
- **Deadlock exposure:** any code path that holds a *card* lock and then creates an account `Transaction` would invert account→card. None was found (a paid payment missing its posting could in theory); the logging in step 1 and the MySQL cases (e) make it visible. `markPaid`'s payment→account→card order is unchanged.
- **Residual:** writes done outside Eloquent (raw SQL/seeders) bypass the hook; the unique promotion indexes remain the last defence for a retry.
- **Decisions for the maintainer:** (1) row locks on `accounts`/`credit_cards` (proposed) versus an advisory `GET_LOCK` per target — row locks match what the code already does and release with the transaction; (2) lock on update/restore as well as create (proposed: yes, they can also produce the matching movement); (3) MySQL tests as an opt-in group with its own config (proposed) versus changing the default suite to MySQL.
