<objective>
Fix `CreditCardCycleService::syncCardBalance()` so it stops silently dropping a card's starting balance. It currently computes `current_balance = sum(expenses) − sum(paid principal)`, with no term for balance not backed by a `CreditCardExpense` row. This fires on every `CreditCardPayment` create/update (via `CreditCardPaymentObserver`) AND nightly for every active card (`credit-cards:generate-cycles`, `routes/console.php`, scheduled `dailyAt('02:00')`), so any card whose balance was ever set directly (a shipped, freely-editable Filament/API field) has its balance silently zeroed/corrupted.

Purpose: this is the root cause of two pre-existing failing tests (`tests/Unit/CreditCardCreditLineSyncTest.php:93`, `tests/Unit/CreditCardKpiServiceTest.php:124`) and a live data-integrity bug affecting real cards. Add a persisted `opening_balance` column (mirrors `Account.opening_balance`) and fix the formula to `opening_balance + expenses − paid principal`. A `creating`-event default (documented in RESEARCH.md section 7, hand-traced against both failing tests) makes both tests pass with **zero modifications** — do not touch either test file in this plan.

Output: one migration, model wiring with the backward-compat default, the corrected service formula, `handleDeletedPayment()` aligned to the same recompute, the additive Filament/API `opening_balance` field, and a new regression test proving pre-existing cards don't drift further under the fix. The at-risk-card audit report (D-10) is a separate plan (21-02) — do not build it here.
</objective>
