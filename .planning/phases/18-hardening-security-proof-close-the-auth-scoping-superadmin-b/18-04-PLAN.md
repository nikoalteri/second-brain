<objective>
Prove and close the credit-card cycle/payment race condition: two near-simultaneous payment-status updates both read the pre-payment state and each apply a full principal reduction, drifting `credit_cards.current_balance` downward by twice the principal.

Purpose: `CreditCardCycleService::syncCycleAndCardFromPayment()` (lines 236-291) adjusts the card balance from a **delta** derived from the caller-supplied `$previousStatus`/`$currentStatus` pair:
```php
if (! $fromPaid && $toPaid)      { $this->balanceService->applyPrincipalPayment($card, $principal); }
elseif ($fromPaid && ! $toPaid)  { $this->balanceService->reversePrincipalPayment($card, $principal); }
```
`CreditCardPaymentObserver::updated()` supplies `$previousStatus` from a static array captured during `updating`. Two concurrent `POST /api/v1/credit-cards/{card}/payments/{payment}/mark-paid` requests both read `status = pending`, both fire the observer with `previousStatus = 'pending'`, and the balance is reduced twice for one payment. `DB::transaction()` narrows but does not close this window (default isolation is not SERIALIZABLE). Drifted balances are explicitly named high severity in D-02, so this is a fix, not a document-and-defer.

The `paid_amount` half of the same method is already safe — it recomputes via `sum('total_amount')` — which is exactly the pattern the balance half should adopt.

Per CONTEXT.md's Claude's Discretion and RESEARCH.md's anti-pattern note: the test DB is SQLite `:memory:` (each connection sees a separate empty database), so **no true parallel-connection concurrency test is attempted**. The proof is a sequenced/interleaved reproduction of the documented race window, matching the existing `CreditCardLifecycleIntegrationTest.php` conventions.

Output: A failing-then-passing reproduction test, an idempotent implementation, and an end-to-end lifecycle regression test.
</objective>

```php
public function syncCycleAndCardFromPayment(int $paymentId, ?string $previousStatus = null, ?string $currentStatus = null): void
{
    $payment = CreditCardPayment::query()->with([...])->find($paymentId);
    if (! $payment || ! $payment->creditCard) { return; }

    DB::transaction(function () use ($payment, $previousStatus, $currentStatus) {
        if ($payment->cycle) {
            $paidAmount = (float) $payment->cycle->payments()
                ->where('status', CreditCardPaymentStatus::PAID)
                ->sum('total_amount');                       // <- already idempotent (recomputed)

            $status = CreditCardCycleStatus::ISSUED;
            if ($payment->cycle->total_due > 0 && $paidAmount >= (float) $payment->cycle->total_due) {
                $status = CreditCardCycleStatus::PAID;
            } elseif ($previousStatus !== null && $payment->cycle->status !== CreditCardCycleStatus::OPEN
                && $payment->cycle->due_date && now()->toDateString() > $payment->cycle->due_date->toDateString()
                && $paidAmount < (float) $payment->cycle->total_due) {
                $status = CreditCardCycleStatus::OVERDUE;
            } elseif ($previousStatus === null) {
                $status = $payment->cycle->status;
            }

            $payment->cycle->update(['paid_amount' => round($paidAmount, 2), 'status' => $status]);
        }

        $card = $payment->creditCard->fresh(['cycles.payments', 'payments']);

        $fromPaid  = $previousStatus === CreditCardPaymentStatus::PAID->value;
        $toPaid    = $currentStatus  === CreditCardPaymentStatus::PAID->value;
        $principal = (float) $payment->principal_amount;

        if (! $fromPaid && $toPaid) {
            $this->balanceService->applyPrincipalPayment($card, $principal);      // <- NOT idempotent
        } elseif ($fromPaid && ! $toPaid) {
            $this->balanceService->reversePrincipalPayment($card, $principal);    // <- NOT idempotent
        }

        $card->refresh();
    });
}
```

The authoritative recompute that already exists in the same class — lines 374-384:
```php
public function syncCardBalance(CreditCard $card): void
{
    $totalExpenses = (float) $card->expenses()->sum('amount');
    $totalPrincipalPaid = (float) $card->payments()
        ->where('status', CreditCardPaymentStatus::PAID)
        ->sum('principal_amount');

    $balance = round(max(0.0, $totalExpenses - $totalPrincipalPaid), 2);

    $card->update(['current_balance' => $balance]);
}
```

What the delta methods actually do — `app/Services/CreditCardBalanceService.php:76-115` (verified: pure arithmetic on `current_balance`, no additional invariants, no credit-limit enforcement):
```php
applyPrincipalPayment($card, $p):   current_balance = max(0, current_balance - $p)
reversePrincipalPayment($card, $p): current_balance = max(0, current_balance + $p)
```
`syncCardBalance()` computes the same quantity from source, so substituting it is behavior-preserving for any card whose balance is fully derived from expenses and paid principal — which is the invariant the console job (`routes/console.php`) already relies on by calling `syncCardBalance()` nightly.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → `POST /credit-cards/{card}/payments/{payment}/mark-paid` | A double-click or retried request can produce two in-flight mutations of the same row |
| Observer → `CreditCardCycleService` | `$previousStatus` crosses this boundary as caller-supplied state captured in a static array, not re-read from the database |
| Service → `credit_cards.current_balance` | Money state; must be derivable from source rows, not from an accumulated sequence of deltas |
