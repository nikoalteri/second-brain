<objective>
Close D-04: prove that `HasUserScoping` correctly no-ops in non-HTTP contexts, so the three shipped scheduled commands actually process every user's records.

Purpose: All three commands query `CreditCard::query()`, `Loan::query()`, and subscription models with **no explicit `user_id` filter** — they depend entirely on `auth()->check()` returning `false` under cron so the `user` global scope adds no `where`. This is correct behavior, but it currently has zero test coverage. If a future change makes the scope fail-closed (e.g. defaulting to a system user), the nightly jobs would silently process only one user's data and nobody would notice. This plan turns the no-op into an asserted contract.

Output: `tests/Feature/ConsoleScopingTest.php` covering all three commands with two-user seed data.
</objective>

Artisan::command('credit-cards:generate-cycles {--month=} {--issue-ready}', function () {
    $service = app(CreditCardCycleService::class);
    $reference = $this->option('month') ? Carbon::parse($this->option('month') . '-01') : now();

    $cards = CreditCard::query()->where('status', CreditCardStatus::ACTIVE)->get();   // <- no user_id filter

    foreach ($cards as $card) {
        $cycle = $service->ensureCurrentMonthCycle($card, $reference->copy());
        if ($cycle->wasRecentlyCreated) { $created++; }
        if ($this->option('issue-ready') && $cycle->status === CreditCardCycleStatus::OPEN
            && $reference->toDateString() >= $cycle->statement_date->toDateString()) {
            $service->issueCycle($cycle);
        }
        $service->refreshCycleStatuses($card->fresh(['cycles.payments', 'payments']));
        $service->syncCardBalance($card->fresh(['cycles.payments', 'payments']));
    }
    $this->info("Cycles ensured: {$cards->count()} cards, {$created} created, {$issued} issued.");
});

Artisan::command('loans:sync-installments {--date=}', function () {
    $scheduleService = app(LoanScheduleService::class);
    $loans = Loan::query()->where('status', 'active')->whereNotNull('start_date')->get();   // <- no user_id filter
    foreach ($loans as $loan) { $scheduleService->generate($loan, onlyMissing: true); }
    $this->info("Loans checked and synced through {$throughDate->toDateString()}: {$loans->count()}.");
});

Artisan::command('subscriptions:sync-renewals {--date=}', function () {
    $service = app(SubscriptionService::class);
    $synced = $service->syncDueRenewals($throughDate);
    $this->info("Subscriptions checked and synced through {$throughDate->toDateString()}: {$synced} renewal(s) processed.");
});

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| cron/CLI → Artisan command | No HTTP request, no authenticated user; the `user` global scope intentionally does not apply |
| Queue worker / ambient-auth process → Artisan command | A command invoked from a process where a user IS authenticated would silently narrow its dataset |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-18-03-01 | Denial of Service (silent data starvation) | `credit-cards:generate-cycles`, `loans:sync-installments`, `subscriptions:sync-renewals` | mitigate | Two-user `assertDatabaseHas` assertions prove every user's records are processed; a future fail-closed scope change breaks these tests (Tasks 1-2) |
| T-18-03-02 | Tampering (drifted balances) | `credit-cards:generate-cycles` run under ambient authentication | mitigate | `test_generate_cycles_command_is_unaffected_by_ambient_authentication` asserts the command is not narrowed by ambient auth; a failure is escalated as a D-02 high-severity finding (Task 1) |
| T-18-03-03 | Information Disclosure | Console context reading all users' rows | accept | Intentional and required for batch processing; there is no cross-tenant recipient in a cron context, and the behavior is now explicitly documented by test rather than assumed |
| T-18-03-04 | Elevation of Privilege | Command invoked by a non-superadmin via an HTTP-triggered path | accept | No HTTP route dispatches these commands (verified: they are registered only in `routes/console.php` and `Schedule::command(...)`) |
</threat_model>
