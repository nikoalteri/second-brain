# Deferred Items — Phase 18

## `TransactionObserver` transfer-pair deletion not transaction-wrapped (lower severity)

- **Finding:** `app/Observers/TransactionObserver.php:47-58` soft-deletes the paired transfer transaction (`$pair?->delete();`) outside any `DB::transaction()` wrapper. If the paired delete throws after the primary transaction's delete has already committed, the pair becomes orphaned — one leg of the transfer is deleted, the other remains.
- **Surfaced by:** 18-RESEARCH.md Open Question 2 (research input carried into execution scope 18-01–18-05) — re-verified against current code at the cited line range during this plan's Task 2 CONCERNS.md re-grounding; not independently re-tested by any of 18-01 through 18-05, since none of those plans' file scopes touched `TransactionObserver.php`.
- **Severity assessment (D-02):** Lower severity — no cross-user data disclosure (only affects the deleting user's own transfer pair), and no corrupted or drifted balances in the common case (the primary delete's `AccountBalanceService::handleDeleted()` call already ran; only the paired transaction's own deletion is unconfirmed). It does not meet the "corrupted/drifted balances" or "broken money math" high-severity bar because no test in this phase reproduced an actual orphaned pair — the risk is theoretical (a delete failing mid-request after the primary commit) rather than demonstrated.
- **Scope decision:** Documented, not fixed in Phase 18. The phase's fix bucket (per D-02/D-03) was scoped to the three confirmed high-severity items closed this phase (see "Not deferred" table below). Promoting this requires reproducing an actual orphaned pair (e.g., forcing the paired `delete()` to throw after the primary delete has committed, then asserting one leg persists) — no test in this phase achieved that reproduction. A future plan should add `DB::transaction()` around the whole `deleted()` handler in `TransactionObserver` and add that reproduction test before or alongside the fix.

## `CreditCardCycleService::handleDeletedPayment()` delta-based balance pattern (lower severity)

- **Finding:** `app/Services/CreditCardCycleService.php:288-330` (`handleDeletedPayment()`) still calls `$this->balanceService->reversePrincipalPayment($card, (float) $payment->principal_amount)` — the same caller-supplied-delta pattern that plan 18-04 replaced with an authoritative `syncCardBalance()` recompute in `syncCycleAndCardFromPayment()` (now at lines 236-286). This method is reachable whenever a `CreditCardPayment` is deleted while `status === PAID`.
- **Surfaced by:** 18-04 Task 2/3 — 18-04-SUMMARY.md's "Out-of-Scope / Deferred" section explicitly names this as `T-18-04-04`, accepted in that plan's threat model, and instructs it be carried forward to this plan's deferred register with a D-02 severity note.
- **Severity assessment (D-02):** Lower severity — this is the *same class* of race (non-idempotent delta on concurrent operations) that 18-04 fixed for the update path, but `handleDeletedPayment()` is reached far less often (payment deletion is rare compared to payment status updates) and 18-04's SUMMARY does not record it as reachable by the exact same interleaving that was reproduced for `syncCycleAndCardFromPayment()` — no test in this phase demonstrated a concrete balance drift via `handleDeletedPayment()`. It fails the high-severity bar because no reproduction exists showing actual corrupted/drifted balances from this specific path, only a structural resemblance to the already-fixed bug.
- **Scope decision:** Documented, not fixed in Phase 18. Promoting this requires the same two-sequenced-call reproduction 18-04 used for `syncCycleAndCardFromPayment()` (e.g., two near-simultaneous payment deletions on the same card racing a stale principal delta), applied to `handleDeletedPayment()` specifically, followed by replacing `reversePrincipalPayment()` with a `syncCardBalance($card)` call to match the pattern 18-04 established.

## `CreditCardCycleService::refreshCycleStatuses()` non-transactional batch loop (lower severity)

- **Finding:** `app/Services/CreditCardCycleService.php:335-362` iterates every cycle on a card and calls `$cycle->update([...])` per row inside a `foreach` loop with no enclosing `DB::transaction()`. Each individual `update()` call is atomic, but the loop as a whole is not — a failure partway through leaves some cycles refreshed and others stale.
- **Surfaced by:** 18-RESEARCH.md (research input to 18-04, the credit-card cycle/payment race-condition plan) — noted as "a secondary but lower-priority fragility point" in RESEARCH.md's State of the Art section; not touched by 18-04's actual task scope (`syncCycleAndCardFromPayment()` only) and not independently tested by any other plan in this phase.
- **Severity assessment (D-02):** Lower severity — no cross-user data disclosure, and no demonstrated drifted balances (the method only touches `paid_amount`/`status`, both idempotently recomputed from source data on every call, so a partial failure followed by a retry self-heals rather than compounding). It fails the high-severity bar because there is no broken money math: re-running the loop after a partial failure produces the same correct end state, it just isn't atomic as a single unit.
- **Scope decision:** Documented, not fixed in Phase 18. Promoting this requires demonstrating a concrete inconsistent-read scenario (e.g., a caller observing the card mid-loop with some cycles refreshed and others not) that actually causes incorrect behavior downstream, since the per-row idempotency currently self-heals on retry.

## Observer static-state residue (`CreditCardPaymentObserver::$previousStatuses`) (lower severity — Branch B)

- **Finding:** `app/Observers/CreditCardPaymentObserver.php:25` (`private static array $previousStatuses = [];`) is not guaranteed to be cleared when an `updating()`-triggered write fails mid-request. `tests/Unit/Observers/ObserverStaticStateTest.php::test_failed_write_does_not_leave_contaminating_static_state` forced a FK violation after `updating()` had already populated the array, and measured non-empty residue (`{"1":"pending"}`) surviving the failed write. The same static-bookkeeping pattern exists at `app/Observers/CreditCardExpenseObserver.php:21` (`$originalPointers`).
- **Surfaced by:** 18-05 Task 2/3 — `tests/Unit/Observers/ObserverStaticStateTest.php` (4 tests) and 18-05-SUMMARY.md's "Decisions Made" section, which documents the measured residue verbatim and the Branch B disposition.
- **Severity assessment (D-02):** Lower severity — no cross-user data disclosure (the static array is per-request/per-process only; no Laravel Octane/Swoole in use, confirmed via `composer.json`, so there is no cross-request persistence), and no corrupted/drifted balance was observed: the same test's follow-up legitimate `mark-paid` update on the same payment id, performed with the stale residue still present, produced the correct `cycle->status === PAID` and `card->current_balance === 0.0`. This is because `CreditCardCycleService::syncCycleAndCardFromPayment()` (post-18-04) recomputes the card balance authoritatively via `syncCardBalance()` rather than applying the caller-supplied `$previousStatus` as a delta, so the stale residue has no path to corrupt the balance. It could still influence the cycle's `OVERDUE` status-decision branch on a subsequent call, but that was not exercised as incorrect by the reproduction.
- **Scope decision:** Documented, not fixed in Phase 18 (Branch B per 18-05's plan-provided branch choice). Both static properties now carry in-code docblocks (added in 18-05) pointing at `ObserverStaticStateTest` and recording the measured residue evidence, so the risk is contractually visible rather than silently unexamined. Promoting this to a fix requires either switching to instance-scoped state (e.g., storing the previous status on the event payload or a request-scoped container binding instead of a static array) or demonstrating a scenario where the residue actually reaches the `OVERDUE` decision incorrectly.

## Resurfaced pre-existing failure: `FinanceReportPageTest` (out of scope, root cause now identified)

- **Test:** `Tests\Feature\Filament\FinanceReportPageTest::test_admin_finance_report_renders_budget_month_context_alerts_and_export_labels`
- **Failure:** `assertSee('exceeded')` fails — the rendered admin finance report page never shows the budget-alert labels the test seeds.
- **Confirmed pre-existing:** First logged in `.planning/phases/17-custom-read-only-finance-chatbot-engine/deferred-items.md`, and independently reconfirmed as pre-existing and out-of-scope by 18-01, 18-02, 18-03, and 18-04's SUMMARY files (each verified via `git stash`/`git log` that the failure predates their own changes). This plan (18-06) reproduces it again during the phase-close full-suite gate (187 passed, 1 failed).
- **Root cause identified during this plan (not previously documented):** `app/Filament/Pages/FinanceReport.php::mount()` sets `$this->selectedBudgetMonth = (int) now()->month`. The test seeds budgets and transactions hardcoded to `2026-04-*` (April) but never calls `Carbon::setTestNow()` to freeze the current date. When the ambient system clock is outside April 2026 (as it is at the time of this phase's execution), the page mounts showing the *current* month's (empty) budget data instead of April's seeded data, so none of the seeded budget-alert labels (`warning`/`exceeded`/`critical`) ever render.
- **Scope decision:** Not fixed in Phase 18. `tests/Feature/Filament/FinanceReportPageTest.php` is not in this plan's (or any 18-0N plan's) `files_modified` scope, and this plan's own `<interfaces>` guidance explicitly instructs: "Phase 17 already logged `FinanceReportPageTest`... — do not re-litigate those, but note if they resurfaced." This finding is noted here with its now-identified root cause (missing `Carbon::setTestNow()` freeze) for a future plan to fix by adding a fixed test-time freeze matching the seeded April 2026 dates.
