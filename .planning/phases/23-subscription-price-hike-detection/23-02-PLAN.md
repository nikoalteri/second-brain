# Plan 23-02 — detect and notify recorded price increases

## Objective

Compare each newly created renewal with its immediately preceding comparable renewal and publish one in-app notification for a positive price change, using Phase 22's condition publisher.

## Read first

`23-CONTEXT.md`, `23-RESEARCH.md`, `23-01-SUMMARY.md`, `SubscriptionService`, `NotificationConditionPublisher`, `ConditionSpec`, `NotificationSeverity`, and Phase 22 notification API tests.

## Work

1. Within `processRenewal()`'s transaction, run detection only after a genuinely new account transaction or card expense is saved. Use the 23-01 combined history. Compare the new amount with the immediately previous **distinct renewal date**, and only when both snapshots show the same currency and frequency. Never skip an incompatible immediate predecessor to compare against an older one. Compare integer minor units or exact decimal strings; any increase of at least one minor unit qualifies, decreases/equal amounts do not.
2. Publish with `NotificationConditionPublisher::publish()` using trigger `subscription_price_hike`, subject `subscription`, subscription ID, renewal date as period key, and warning severity. Use an internal subscription URL. State the previous and new **recorded automatic renewal** amounts and absolute delta in the correct currency, without claiming an observed bank charge. If the publisher fails, roll back the posting and renewal-date advance together.
3. Keep the trigger event-based: do not put it in `FinanceNotificationEvaluator::TRIGGERS`, reconcile it away, or add a second notification UI/channel. No retroactive scan and no notification for a mere configured price edit before a new posting.

## Acceptance and verification

- Integration tests cover 13.99 to 15.99, +0.01, equal/decrease, first renewal, legacy unknown metadata, changed frequency/currency, monthly/annual amounts, account-to-card and card-to-account switches, and same-date retry/concurrent-insert recovery. Assert one linked notification and correct owner/date, not only a service call.
- A failed notification write leaves no new charge, balance change or date advance. A successful retry publishes once. A second run of `subscriptions:sync-renewals` creates no duplicate notification.
- Run targeted renewal/notification tests, then full backend suite. On UAT, verify one deliberately controlled renewal with non-sensitive test data and check the bell and linked subscription. Record the unresolved MySQL two-connection race if no suitable test environment exists.

## Output

Create `23-02-SUMMARY.md`; update ROADMAP/STATE to implemented only after tests and UAT verification. Keep the UAT missing-renewal observation tracked separately if it is still unresolved.
