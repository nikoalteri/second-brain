# Plan 23-01 — reliable renewal-charge history

## Objective

Make newly posted subscription renewals an immutable, comparable history across account and card billing, and verify the reported UAT gap before building price-hike detection on top of it.

## Read first

`23-CONTEXT.md`, `23-RESEARCH.md`, `SubscriptionService`, `SubscriptionRenewalIdempotenceTest`, the two posting models and their migrations, `routes/console.php`, and Phase 22's notification publisher. Use the actual `uat` source for exact schema and observer behavior.

## Work

1. After the next scheduled UAT renewal run, perform a read-only check of the affected subscriptions and their linked charges. Confirm whether the VM-off window alone explains the gap, whether the rows are card expenses rather than general transactions, or whether a reproducible posting defect remains. Record only IDs, dates, source and presence/count in the report; do not copy personal financial details into planning artifacts. If a defect remains, add its regression test and fix it in a separately reviewable change before declaring this plan complete.
2. Add nullable billing-frequency and currency snapshots to both automatic-renewal posting tables and their model fillable/casts. Populate them at creation from the subscription's frequency and the billing source's currency. Do not assign current metadata to existing historical rows without evidence. Keep old rows and indexes intact; document the legacy-baseline limit.
3. Refactor both upsert paths to report insert versus existing row. Preserve the original amount and snapshots on a retry, including the concurrent unique-key recovery path. Verify that account balance/card balance and `next_renewal_date` advance exactly once. Treat a soft-deleted same-date account posting as an existing renewal under the current restore policy, not a new charge for alerting.
4. Provide an owner-scoped query/value object for the two latest distinct renewal postings across account and card paths, ordered by `subscription_renewal_date` (stable tie rule for duplicates). Normalize sign and expose amount, source, frequency snapshot and currency snapshot. Reject or explicitly handle ambiguous same-date cross-table rows; never use another owner's posting.

## Acceptance and verification

- Tests cover account and card inserts, overdue catch-up after a missed scheduler day, retries with a changed configured price, soft-deleted restore, source switch, missing source/currency, owner scoping and ambiguous same-date history.
- A retry keeps the original posted amount and causes no second balance movement. New rows have snapshots; legacy rows remain unchanged.
- Run targeted subscription tests and the full backend suite. Record the read-only UAT finding separately from automated test results; do not infer that local tests prove the UAT scheduler ran.

## Output

Create `23-01-SUMMARY.md` with migration, history contract, test evidence and UAT finding.
