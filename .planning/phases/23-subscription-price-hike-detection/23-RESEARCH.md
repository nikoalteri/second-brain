# Phase 23 — implementation research

**Prepared:** 2026-10-17. Current `uat` source is authoritative over older planning notes.

## Confirmed integration points

- `SubscriptionService::syncDueRenewals()` selects active subscriptions with `auto_create_transaction = true` and `next_renewal_date <= today`; its loop processes every overdue renewal until the date advances beyond today. `subscriptions:sync-renewals` runs at 01:55 through the VM's per-minute cron. If the VM was off at that time, the next successful scheduled run should catch up. An account-billed renewal creates a `Transaction`; a card-billed renewal creates a `CreditCardExpense`, which is not in the general transaction list.
- `processRenewal()` holds the subscription row lock and posts a charge and advances `next_renewal_date` in one database transaction. Both posting tables have a unique key on `(subscription_id, subscription_renewal_date)`. `upsertTransaction()` and `upsertCreditCardExpense()` currently update an existing renewal row with today's configured amount on a retry; that can rewrite the historical comparison baseline. The new detector must distinguish an insert from an existing row and preserve the amount of an already-posted renewal.
- Both posting tables link the subscription and renewal date, but neither snapshots the billing frequency or currency. A transaction's source account has `currency`; a card expense's card links to an account. Currency and frequency can later change, so today's subscription/account state is not proof of an older charge's unit or cadence. Do not backfill unknown metadata by copying current values to old rows.
- Phase 22 supplies `NotificationConditionPublisher::publish($userId, ConditionSpec)` and the owner-scoped REST/SPA bell. A price increase is an event keyed by subscription and renewal date, not an active state to reconcile in the daily digest. A separate `subscription_price_hike` trigger can publish directly in the renewal transaction with `period_key = YYYY-MM-DD` and `warning` severity. The database condition/notification uniqueness keys protect retries.
- The renewal amount is generated by `getBillingAmount()` from configured subscription cost; it is a **recorded expected charge**, not an independently observed vendor/bank debit. No bank-import confirmation exists in Phase 23. Notification copy must say this explicitly and avoid "bank-confirmed" wording.

## Planning decisions

1. Preserve the context's `> 0` threshold, automatic-posting-only scope, and consecutive renewal comparison. Compare a new renewal with the immediately preceding posted renewal for that subscription across both account and card sources. Never scan a separate source-specific history that loses the predecessor after a source switch. Exclude soft-deleted transactions from the comparable history.
2. Add nullable immutable frequency/currency snapshots to both posting tables for new automatic renewals. Use the subscription's frequency ID and the billing source's currency at posting time. A card without a resolvable linked-account currency must be explicitly handled as unknown, not silently assumed EUR. Compare only when both current and previous postings have known matching frequency and currency. Legacy rows without trustworthy snapshots remain usable as history but are not a comparable baseline; the first alert may therefore require two newly snapshotted renewals. Record that limitation in acceptance/UAT notes.
3. Make the posting service return whether it created a new charge. Only a new charge is eligible for price-hike detection. Reprocessing an existing renewal must not change its amount or metadata, post a second balance movement, or emit a notification. Check the existing account/card behavior and regression tests before changing it.
4. Use decimal-string or integer-minor-unit comparison for the amount; the sign convention is negative for transactions and positive for card expenses. Format absolute before/after/delta values with the common currency. A source switch is comparable only when the snapshotted currency and frequency match.
5. Publish through the Phase 22 publisher in the same database transaction as the new posting and date advance. A notification failure must roll the whole renewal back for safe retry. Key the condition by `subscription_price_hike`, `subscription`, subscription ID, and the renewal date. There is no daily reconciliation or retroactive scan of older price changes in this phase.

## UAT observation to verify separately

The user saw old subscription renewals missing from transactions while the VM had been off. This is not yet a confirmed code defect. After the VM has run its next 01:55 schedule, inspect only the affected owner's active subscriptions: `auto_create_transaction`, `next_renewal_date`, account/card source, and linked `subscription_renewal_date` rows. Check the scheduler/command log and distinguish account transactions from card expenses. If overdue active renewals are still missing, reproduce with a targeted test and fix the posting path before relying on its history. Do not manually create or backfill financial rows in UAT without reviewing the exact expected dates and balance impact.

## Verification risks

- SQLite tests do not prove MySQL `FOR UPDATE` behavior. Phase 22's two-connection MySQL concurrency gap also applies to direct event publishing.
- A mixed account/card history may contain same-date rows in both tables from a source switch; the implementation must choose one canonical renewal or reject ambiguity rather than notify twice.
- A deleted historical transaction is not a reliable prior charge; a restored same-date posting is a retry, not a new increase.
