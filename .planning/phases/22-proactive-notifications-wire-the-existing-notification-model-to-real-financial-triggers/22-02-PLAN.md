# Plan 22-02 — financial triggers and scheduled digest

## Objective

Evaluate the four agreed finance triggers once daily for each owner, send new or escalated conditions through the 22-01 publisher, resolve stale conditions, and clean old read notifications.

## Read first

`22-CONTEXT.md`, `22-RESEARCH.md`, `22-01-SUMMARY.md`, `BudgetService`, `BudgetAlertService`, `CreditCardPayment`, `LoanPayment`, `Subscription`, their status enums, `UpcomingPaymentsService`, `User`, and `routes/console.php`.

## Work

1. Implement an evaluator taking an explicit owner ID and a calendar date. For the current month, call `BudgetService::getMonthlyOverview()` and use its `alert_status`; do not recalculate budget thresholds. Emit category/month conditions for warning, exceeded and critical.
2. Emit card-limit conditions for active cards with `credit_limit > 0` and `current_balance >= 90%` of that limit. Emit unpaid card-payment conditions once their due date is reached, including overdue payments. Query payments through cards owned by the explicit owner; do not assume payment rows have `user_id`.
3. Emit unpaid loan-payment conditions due in 0–3 calendar days or overdue, through loans owned by the explicit owner. Emit active subscription renewal conditions due in 0–3 calendar days, with the renewal date as the period key. Use consistent date boundaries and status enum values. Suppress conditions when parent records are deleted/inactive or payment status becomes paid; reconcile the owner's previously active conditions afterward.
4. Register a `finance:notifications-digest {--date=}` Artisan closure in `routes/console.php` and schedule it for 02:05 with `withoutOverlapping()`. Iterate active users explicitly; isolate/log per-owner failures and return failure if any owner failed. The service and command must not depend on ambient `auth()` or silently widen a user query under a superadmin context.
5. During the digest, permanently delete only notifications whose `read_at` is more than 90 days old. Keep condition rows and unread notifications. Use a bounded batch for cleanup if needed.

## Acceptance and verification

- Feature tests create actual budget/transaction, card/payment, loan/payment, and subscription rows for two owners; assert only the intended owner's notifications, correct thresholds and date edges, no duplicates on repeated command runs, payment/renewal resolution, and budget escalation/reactivation.
- Test one owner throwing during evaluation while another is still processed and the command returns failure.
- Test retention against read and unread rows and confirm cleanup does not reopen a condition.
- Assert the command is scheduled once at 02:05 after existing finance jobs and guarded by `withoutOverlapping()`; run the targeted command tests and a manual `artisan` dry run against test data if practical.

## Output

Create `22-02-SUMMARY.md` with trigger behavior, schedule, and test results.
