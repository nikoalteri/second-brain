# Plan 22-01 — durable notification condition lifecycle

## Objective

Build the persistence and publishing contract that lets the daily evaluator create at most one notification per active condition, while keeping reading, cleanup, resolution, escalation, and later reactivation distinct. Phase 23 must be able to publish through the same contract.

## Read first

`22-CONTEXT.md`, `22-RESEARCH.md`, `app/Models/Notification.php`, the notifications migration, `app/Traits/HasUserScoping.php`, and the current migration/model conventions. Use the source schema rather than the context's assumed columns.

## Work

1. Add a migration for a `notification_conditions` table with owner FK, `trigger`, `subject_type`, `subject_id`, `period_key`, `active`, `current_severity`, `max_notified_severity`, `episode`, `activated_at`, `resolved_at`, and timestamps. Add a unique key over owner/trigger/subject/period and an index for scanning active rows by owner. Keep `period_key` non-null, including a constant for an open-ended card-limit condition. Choose column lengths that fit MySQL's composite-index limit.
2. Add the missing nullable `related_model` and `related_id` columns to `notifications`, plus a nullable `notification_condition_id` FK with `nullOnDelete`, nullable episode and severity fields, and a unique key on condition/episode/severity. Existing notifications must migrate without data changes. Add matching casts/relations to models; do not remove existing `Notification` fields or change the existing `type` enum.
3. Implement a service with an explicit `userId` and a value object/structured input for trigger, subject, period, severity, text and internal URL. Its publish/reconcile operation must: create a notification atomically for a new condition; do nothing for a repeated condition at the same or lower previously notified severity; create one escalation notification when severity exceeds the episode's prior maximum; update current severity when it falls; mark unseen active conditions resolved; and create a fresh notification and increment the episode when a resolved condition becomes true again. Reconcile only after the owner's evaluation completes successfully. Ensure concurrent runs cannot create duplicates using both unique keys and transaction/row locking with unique-conflict recovery. Reading or deletion of a notification must never change its condition.
4. Keep the service independent of the four specific trigger queries so later phases can reuse it. Restrict accepted `action_url` values to application-relative paths when writing.

## Acceptance and verification

- Feature tests cover same-day and next-day reruns, a read notification, a deleted/cleaned notification, escalation, resolution and reactivation, plus owner separation. Assert notification counts and condition state, not just service calls.
- Migration tests prove existing notification rows remain readable and the new unique key rejects duplicate condition identities.
- A concurrent-run test proves the uniqueness invariant on MySQL where available; if only SQLite is available, record the unverified database-specific locking behavior in the summary.
- Run targeted PHPUnit tests for the condition service and migrations. The plan is complete only when a later phase can call the publisher without reimplementing deduplication.

## Output

Create `22-01-SUMMARY.md` with schema, lifecycle rules, test evidence, and any MySQL verification gap.
