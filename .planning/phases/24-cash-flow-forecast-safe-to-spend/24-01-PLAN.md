# Plan 24-01 — classify 30-day commitments

## Objective

Produce a deterministic, owner-scoped set of upcoming and overdue obligations whose accounting state is explicit enough for a forecast. Preserve the existing upcoming-payments/chatbot response.

## Read first

`24-CONTEXT.md`, `24-RESEARCH.md`, `UpcomingPaymentsService`, `SubscriptionService`, `LoanPaymentPostingService`, `CreditCardPaymentPostingService`, the three payment models, subscription posting models and their tests.

## Work

1. Define a read-only forecast obligation shape: type, source record/date identity, due date, billing account/card IDs, currency, face amount, cash-outflow amount, posting state, and coverage/exclusion reason. Scope every root and relation to the requested owner, including when that owner is a superadmin. Unknown or inconsistent source data must be explicit.
2. Collect all existing loan installments and card payments due in the inclusive 30-day interval, plus overdue not-settled rows for coverage. Resolve live posting transactions and whether their account balance already moved; status alone is insufficient for loan installments. Do not count card expenses as bank-account debits.
3. Project active subscription renewals across the entire window using `calculateNextRenewalDate()` and `getBillingAmount()`, including missed/overdue first occurrences as coverage. Match an existing posting by subscription ID + renewal date on either account or card path, taking soft deletes and Phase 23's cross-table idempotence policy into account. De-duplicate occurrences. Account renewals are potential cash debits; card renewals are separate card-charge information, never a second deduction next to a card payment.
4. Add focused service tests proving the edge cases in `24-RESEARCH.md`, especially posted-but-pending loan, same-date posted renewal, two renewals within 30 days, overdue items and card expense/payment overlap. Keep the original `UpcomingPaymentsService` tests and chatbot equality test passing.

## Acceptance and verification

- Every classified obligation has one stable identity and clear inclusion/coverage state. No user's financial row can enter another user's forecast.
- Already reflected account postings and card-financed subscription charges cannot cause a second bank-balance deduction.
- Run targeted backend tests and existing upcoming-payments/dashboard/chatbot tests. Record any state that cannot be determined from current schema as an explicit coverage reason.

## Output

Create `24-01-SUMMARY.md` with the obligation contract, edge-case test evidence and unresolved coverage conditions.
