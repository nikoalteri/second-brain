# Phase 24 — implementation research

**Prepared:** 2026-10-17 against current `uat` source. Code takes precedence over the older context's reuse assumption.

## Confirmed behavior

- `UpcomingPaymentsService::forUser($user, $days)` is owner-scoped even for superadmins and supplies loan, card-payment and subscription reminders. It only queries due dates from today through today + N. Loan and card rows expose a linked posting transaction; subscriptions expose a Boolean posting check, source type and billing amount. The dashboard currently requests only three days. Keep that existing endpoint/chatbot contract stable.
- The service is a candidate list, not a cash-flow ledger: it omits overdue items, returns only one subscription renewal, has no currency or source-account ID, and may include an amount already reflected in `Account.balance`. A forecast cannot safely sum its `amount` fields directly.
- A due loan installment creates a `Transaction` through `LoanPaymentPostingService` even while its status is `pending`; the posting, rather than status, determines whether the account balance already moved. Card-payment posting occurs on `paid` status. For subscriptions, account billing creates a `Transaction`; card billing creates a `CreditCardExpense` and does not itself debit the account. Phase 23's renewal rows carry currency/frequency snapshots for newly posted charges; old rows may lack them.
- `Account` has `balance`, `currency`, `is_active`; `SavingGoal` has `account_id` and active status. `Loan.account_id`, `CreditCard.account_id`, and `Subscription.account_id` or `credit_card_id` supply the source. A card has no own currency; its linked settlement account supplies it. The current Dashboard client sums all account balances and formats them as EUR by default; that convention is unsuitable for this new forecast.
- `SubscriptionService::calculateNextRenewalDate()` advances by `months_interval` using month-end clamping and configured `day_of_month`. `getBillingAmount()` returns the actual configured billing amount. Reuse both for projected occurrences, with a fixed upper bound of 30 days and a de-duplication key of subscription ID + renewal date.
- Phase 25 import/reconciliation has no implementation in the current source. Consequently this phase cannot assert that bank balances are reconciled. Phase 26 also adds dashboard totals; give the forecast its own response and component so both can coexist.

## Planning decisions

1. Use a dedicated owner-scoped forecast service and `GET /api/v1/dashboard/cash-flow-forecast`. It may reuse the existing upcoming-items query for discovery, but must resolve source accounts, currency, posting state, recurrence and overdue coverage from the underlying records. Do not change the existing three-day reminders or chatbot semantics just to make them act like forecast data.
2. Fix the horizon as local calendar dates `today` through `today + 30 days`, inclusive, and return `as_of` and `through_date`. Past-due unpaid/unposted obligations should be visible in a separate overdue coverage list, not silently added to a 30-day due-date total. If any such item affects a counted account, mark the projection incomplete. Do not imply the figure includes unmodelled income or expenses.
3. For each currency, start with active, owner-owned account balances except an account linked to an active, owner-owned savings goal. The entire linked account is excluded (D-03). Group by ISO currency; no FX conversion or cross-currency grand total. Unknown-currency accounts and obligations are disclosed separately and prevent a complete figure. Use decimal strings/integer minor units for aggregation, with rounding only at the API boundary.
4. Model each obligation with stable identity (`type`, record ID, due date), source account/card, currency, face amount, amount still to be debited from the included account balance, posting state and an exclusion/uncertainty reason. Loan/card-payment postings already reflected in the account balance contribute zero; pending unposted items contribute their remaining amount. For account-billed subscriptions, a matching live posting contributes zero; an unposted renewal contributes its billing amount. An obligation paid from an excluded/inactive account remains in the breakdown but is not deducted from the available pool. A missing or foreign source is never guessed.
5. Card-billed subscription renewals are projected card charges, not direct account cash outflows. Never add them to the deduction alongside the card's cycle payment. Count the authoritative `CreditCardPayment.total_amount` once for each existing due payment; disclose card charges that cannot be proven covered by a due cycle (including future renewal occurrences) as a coverage caveat. Do not invent future card-payment amounts from card expenses. A later phase can add a card-cycle simulation if needed.
6. The result is a **known-commitments estimate**, not a guarantee of spendability. Return per-currency `available_balance`, `counted_commitments`, `estimated_remaining`, item breakdown and coverage codes/counts. The UI must state that unknown future spending/income and unreconciled bank data are outside the estimate. With overdue, unresolved source/currency or uncovered card charges, show the partial estimate with a prominent incomplete state rather than an unqualified “safe to spend” claim.

## Edge cases to prove

- Posted pending loan on its due date; paid card payment with a posting; deleted/soft-deleted posting; manual subscription with no auto-posting; account versus card renewal; a card expense plus card payment in the same window; recurring monthly subscription with two dates inside 30 days; subscription whose `next_renewal_date` is overdue; excluded goal account; inactive source account; unknown currency; mixed EUR/USD; another user's rows and superadmin's personal view; empty accounts/commitments; month-end and daylight-saving boundaries.
- A soft-deleted account transaction is not reflected in balance and must not suppress a deduction merely because a historical row exists. Validate this against transaction observer behavior during implementation. For a renewal that has a soft-deleted same-date row but cannot be re-posted under the current restore policy, mark coverage incomplete rather than silently treating it as settled.
- No new database table or snapshot migration is required by the planned read-only API. If implementation discovers the existing records cannot distinguish a material settlement state, stop that subpath and surface an explicit coverage reason rather than guess.
